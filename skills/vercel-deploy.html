vercel-deploy

Answer "is it live?" for Vercel projects and manage deployments via the Vercel REST API (curl + jq, zero-deps). Triggers on vercel, is it live, deploy status, production deploy, redeploy.

Scrubbed of personal details for the public library. The full library is re-curated weekly.

Vercel Deploy

Purpose

Deterministically answer "is it live?" for any Vercel project: compare the deployment serving the production domain against the repo's origin/master commit SHA. Also covers deployment inspection and redeploy triggering (approval-gated).

Tooling

Zero-deps: curl, jq. The vercel CLI is not installed on this VM — use the REST API at https://api.vercel.com directly.

Auth

Send the API token as Authorization: Bearer $VERCEL_TOKEN.

  • The token is created by the user at vercel.com/account/tokens and stored in the Secure Vault; the parent agent handles collection. This skill never collects, fabricates, or persists tokens.
  • Every curl below assumes VERCEL_TOKEN is set in the environment.

Degraded mode (no token)

Without a token, do unauthenticated HTTP spot-checks of the live site:

# Status + asset-filename grep against the deployed page
curl -fsSL --max-time 15 https://hoops.dumbmodel.com/ -o /tmp/live.html \
  && grep -o 'mtnn_attr_topk\.bin\|timesfm-forecast\.js' /tmp/live.html | sort -u

A 200 plus the expected asset filenames means the page serves the new build. It cannot confirm the commit SHA — treat as "likely live", not proof.

Operating Rules

  1. Read-only API calls (GET) are safe to run freely.
  2. Never trigger a redeploy or promote a deployment without explicit user approval. This skill documents the redeploy call only.
  3. Always compare the deployed commit SHA against the repo's origin/master SHA when answering "is it live?":

``bash git -C ~/workspace/vector-hoops ls-remote origin HEAD | cut -f1 ``

  1. The Vercel project id is not the project name: resolve it once via GET /v9/projects/<name> and reuse.

Recipes

1. List recent deployments (state, SHA, time):

curl -fsSL --max-time 20 -H "Authorization: Bearer $VERCEL_TOKEN" \
  "https://api.vercel.com/v6/deployments?project=<PROJECT_ID>&limit=5" \
  | jq -r '.deployments[] | "\(.createdAt / 1000 | strftime("%Y-%m-%d %H:%M")) \(.state) \(.meta.githubCommitSha // "?") \(.url)"'

state is one of READY, ERROR, BUILDING, QUEUED, CANCELED, INITIALIZING.

2. Inspect one deployment:

curl -fsSL --max-time 20 -H "Authorization: Bearer $VERCEL_TOKEN" \
  "https://api.vercel.com/v13/deployments/<DEPLOYMENT_UID>" \
  | jq '{state: .readyState, url: .url, alias: .alias, sha: .meta.githubCommitSha}'

Note: on /v13 the readiness field is readyState (.state is absent/null) — poll on readyState (READY, ERROR, BUILDING, QUEUED, CANCELED, INITIALIZING).

3. Which deployment does the production domain serve?

curl -fsSL --max-time 20 -H "Authorization: Bearer $VERCEL_TOKEN" \
  "https://api.vercel.com/v3/aliases/hoops.dumbmodel.com" \
  | jq '{domain: .domain, deploymentId: .deploymentId}'

Then feed deploymentId into recipe 2 and compare its sha with origin/master.

4. Answering "is it live?" (the decision procedure):

  1. Get origin/master SHA from the repo.
  2. Get the deployment UID behind the production domain (recipe 3).
  3. Inspect that deployment (recipe 2).
  4. Report: LIVE only if state == READY and sha == origin/master SHA. Otherwise report DEPLOYING / STALE / FAILED with the actual values.

5. Trigger a redeploy (approval-gated, document only):

# NEVER run without explicit user approval
curl -fsSL --max-time 30 -X POST -H "Authorization: Bearer $VERCEL_TOKEN" \
  -H "Content-Type: application/json" \
  "https://api.vercel.com/v13/deployments" \
  -d '{"name": "<PROJECT_NAME>", "gitSource": {"type": "github", "repoId": "<REPO_ID>", "ref": "main"}}'
