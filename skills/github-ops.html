github-ops

GitHub repo operations via the gh CLI: PR status and checks, CI logs, merges, and releases. Triggers on 'github', 'gh cli', 'PR status', 'CI checks', 'merge PR', 'release'.

Scrubbed of personal details for the public library. The full library is re-curated weekly.

GitHub Ops

Purpose

One job: operate the owner's GitHub repos from the terminal. Read status, inspect CI, and ship PRs and releases — always from a local clone, never from a hand-typed URL.

Tooling

The gh CLI, backed by the owner's authenticated session. Every command below was verified working 2026-09-07.

PR status and checks

cd ~/workspace/<repo>            # always work from the clone
gh pr status                     # your open PRs + review requests for this repo
gh pr checks <number>            # CI check results for a PR
gh pr view <number>              # PR title, body, diff stat, review state

CI logs

gh run list --limit 10           # recent workflow runs
gh run view <run-id>             # run summary
gh run view <run-id> --log-failed  # failed step logs only

Merge (requires explicit user approval every time — see Operating Rules)

gh pr merge <number> --squash    # squash-merge (default for feature branches)
gh pr merge <number> --merge     # merge commit (for integration branches)

Releases (requires explicit user approval every time)

gh release list --limit 10
gh release view <tag>
gh release create <tag> --title "<title>" --notes "<notes>"

Repo info and search

gh repo view                     # current clone's repo
gh search repos --owner owner   # list the owner's repos

Auth

Already configured. gh auth status shows: logged in to github.com as owner, token scopes gist, read:org, repo, workflow. No setup needed; if a command fails with 401/403, re-run gh auth status and gh auth refresh before anything else.

Operating Rules

  1. Never merge or release without explicit user approval. Read-only commands (pr status, pr checks, run list, repo view, release list) are safe to run freely. gh pr merge and gh release create require a clear yes from the user in the current conversation — a standing "keep pushing" does not count.
  2. Always use the clone's configured remote. Run gh from inside the repo directory so it resolves the remote itself. Never hand-type a repo URL: the hand-typed jcamd/vector-hoops returns "Repository not found" while the real repo is owner/vector-hoops. A "not found" from a hand-typed URL is a false alarm, not a real failure.
  3. Prefer --squash for feature branches (scout/<slug>), --merge only for integration branches. This matches the scout → PR → review → merge → release workflow.
  4. Report CI failures with the failed step and its log excerpt, not just the red X. Use gh run view <run-id> --log-failed.
  5. After any merge, confirm the new HEAD with git log --oneline -3 in the clone before claiming anything shipped.
