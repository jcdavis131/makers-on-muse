social_competitor_analysis

Compare the user's business with competitors using public Instagram profiles, posts, follower changes, and grounded account metrics.

Scrubbed of personal details for the public library. The full library is re-curated weekly.

Social Competitor Analysis

Purpose

Use this skill for competitor discovery and comparison, peer benchmarks, public Instagram follower growth, posting cadence, top posts, format mix, positioning, and product-launch analysis. An implied peer set such as "brands my size" or "my industry" also belongs here.

Use social_content_performance when every account or post being compared belongs to the user and no peer benchmark is requested.

Commands

Run these Instagram analytics commands through exec:

instagram-cli accounts
instagram-cli analytics-metric-metadata \
  --account-id <user_own_fbid> --metric-name <metric>
instagram-cli analytics-top-post \
  --account-id <user_own_fbid> --username <handle> --days 30 [--include-text]
instagram-cli analytics-follower-count-delta \
  --account-id <user_own_fbid> --username <handle> --days 28
instagram-cli analytics-metric-cards \
  --account-id <user_own_fbid> --username <handle> --days 28

Handles may be repeated. Use at most 10 handles in one call and batch accounts that are being compared so they share one window.

Use social.search to discover public social accounts or posts and browser.search for broader public-web discovery. Use the installed Instagram CLI for structured profiles and posts, following its access and identifier rules. Search results identify candidates; they do not establish account facts until a profile or analytics command returns those facts.

There is no direct product-launch command. For a launch or drop comparison, read the relevant public posts through the Instagram CLI and synthesize only what those posts explicitly support.

Workflow

1. Resolve the execution account

Begin with instagram-cli accounts and use a returned user_fbid as --account-id. This selects the authenticated execution context; it is not the competitor identifier.

  • If exactly one linked account is returned, use it.
  • If several linked accounts are returned and the request does not identify

one, ask one concise question listing their handles, then stop until the user chooses.

  • If a named user account is absent, explain that it cannot be used as the

owned side of the comparison. Do not substitute another account.

Never show opaque account or post IDs to the user.

2. Resolve competitors and scope

Use handles supplied by the user. Otherwise use social.search or browser.search to find candidates, then resolve each candidate with a structured Instagram profile command before including it.

Do not invent handles from brand names. If a candidate cannot be resolved, drop it rather than replacing it silently. State Instagram and the time window used. Compare values only when the accounts share the same metric, window, and completeness.

3. Read the evidence

  • Use instagram-cli analytics-top-post when the task asks for the most-liked

post. Add --include-text whenever the post will be named, summarized, or displayed so its label can be grounded in returned content.

  • Use instagram-cli analytics-follower-count-delta for follower changes. An

empty daily series means insufficient history, not zero growth.

  • Use instagram-cli analytics-metric-cards for comparable cards. Check every

account's window.complete and errors before comparing. Render card values and growth_display verbatim; never convert the ratio to a percentage.

  • Resolve every Instagram metric shown with

instagram-cli analytics-metric-metadata. Copy the returned display name and definition; never invent either.

Use public metrics only for competitor accounts. Never state or estimate their private reach, impressions, saves, shares, audience demographics, paid spend, revenue, conversion data, or other owner-only signals.

4. Analyze without invention

  • Join results by resolved handle or echoed request identifier, never by array

position.

  • Treat missing and null as unavailable, never zero.
  • Compare only complete, like-for-like values from the same platform, metric,

grain, and window. Show an incomplete account as a gap rather than ranking it.

  • Preserve backend-provided deltas, ratios, summaries, and rankings. Do not

recompute them from rounded display values.

  • Separate posting frequency from performance; the most-posted format is not

automatically the best-performing format.

  • A top-post result proves only which returned post had the most likes. One top

post per account cannot establish that its subject, format, person, or creative treatment tends to outperform. Do not turn a shared trait of top posts into a trend, finding, or recommendation without a comparison set that supports it.

  • Show a post only when its returned publication date falls inside the stated

comparison window. If the tool returns an out-of-window post, omit it and say that in-window post evidence was unavailable.

  • Do not infer causes, intent, demographics, sensitive traits, private metrics,

or audience sentiment from public content or correlations.

Scope every absence, gap, or whitespace claim to the accounts and posts actually returned. Before claiming top, best, highest, lowest, most, none, a count, or a ranking, verify that the complete eligible set and the relevant field were returned for the stated window. Keep that completeness in the analysis; do not display every item unless the user asks for the full set.

Prioritize the few comparisons that most directly answer the request. Support each finding with values from both sides and name its scope. Omit secondary patterns unless they materially qualify the conclusion. Recommend a category-level action only when it follows from a supported comparison; promise no outcome and do not turn it into targeting, outreach, disparagement, or instructions to copy a competitor's creative strategy.

5. Present the result

Lead with the answer. Name Instagram, the actual returned window, and the comparison scope. Present only the strongest findings and the examples needed to support them. If a ranking covers many accounts or posts, state the analyzed population but show only the relevant leaders unless the user requests the full ranking. Put an availability or evidence-limit note beside the claim it qualifies.

Use concise prose for the answer, interpretation, and caveats. Choose supporting presentations according to what the evidence needs:

  • Use a metric-card widget only for a non-comparative snapshot of distinct

headline KPIs for one account and one window; a card may include a subdued prior-period delta as context.

  • When presenting a comparison between subjects, use a Markdown table for exact

values or a chart when the relative shape matters.

  • Use no supporting presentation when prose communicates the result clearly.

Combine formats when each communicates a distinct part of the answer. Avoid repeating the same data across prose, widgets, and tables unless the repetition is necessary to support a conclusion. Create a widget only when it adds clear value.

A metric-card grid is a visual dashboard of independent cards, never a Markdown table or an HTML table. Its cards show different KPIs for the same subject, not the same KPI repeated across comparison subjects. Each card contains a short label, one prominent value, and optional subdued prior-period context such as +12% vs prior 28d.

Build metric cards with a responsive CSS grid using repeat(auto-fill, minmax(260px, 1fr)). Give each card its own rounded border and consistent padding. Every card remains one normal grid cell; never stretch a leftover card across the row or use grid-column spanning. Avoid table headers, rows, cells, gridlines, gradients, gauges, decorative icons, heavy shadows, and oversized type.

Keep any widget responsive and restrained, using only --hatch-widget-* colors. Build it with widget.create, kind: "html", and present_now: false. If creation fails, answer without the widget and do not fetch again.

Label a displayed post with the first five words of its returned caption, adding an ellipsis only when more words follow. If no caption is available, use its returned date and format. Reuse the label consistently and link every singled-out post with its exact returned permalink. Never construct a permalink or expose a raw ID. If no verified link exists, describe only the supported aggregate pattern.

Restricted content

Do not surface, rank, profile, or compare accounts in regulated or sensitive verticals, including housing, employment, credit or financial services, politics or issue advocacy, pharmaceuticals, medical services, health insurance, or supplements making health claims. If classification is genuinely ambiguous, exclude the account rather than searching for sensitive evidence.

Do not infer or report sensitive personal characteristics about an account, creator, audience, or commenter. Omit posts involving graphic harm, weapons, drugs, adult sexual content, tragedy, hate, scams, or illegal goods. If content is omitted, say only that some content was excluded for safety; do not name the sensitive category.

Final checks

Before replying, verify:

  • the execution account came from the instagram-cli accounts result;
  • every competitor was resolved from current public data;
  • every number belongs to the named account and window;
  • all compared windows are complete and like-for-like;
  • missing values were not converted to zero;
  • metric names and definitions match metadata;
  • the answer contains only the most useful findings and supporting examples;
  • any widget adds a useful chart rather than duplicating the response;
  • no private metric, sensitive inference, raw ID, tool name, or backend field

name appears in the user-facing answer.
