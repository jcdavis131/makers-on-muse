Diagnose a failure with the three-way attribution test (recipe problem / knowledge gap / ambiguity), route the fix to the right layer, and review it with fresh eyes before landing. Use on any mistake, verifier failure, user correction, or regression.

Scrubbed of personal details for the public library. The full library is re-curated weekly.

Mistake Attribution

Purpose

Turn every failure into a correctly-routed, permanent fix. Adapted from the organizational-second-brain pattern: separate what the agent knows from how it reasons, so each correction lands in the right layer instead of becoming a vague "lesson."

The Attribution Test

Ask exactly one question first:

Could the agent have reached the correct conclusion from its source materials (skills, memory, docs, briefs it actually loaded)?

  • Yes, but it didn't → recipe problem. The knowledge was there; the

procedure failed. Fix the workflow: edit the skill, the brief, the checklist, or the recipe that ran. Do not add more knowledge.

  • No → knowledge gap. The materials didn't contain the answer. Add it:

a memory entry, a knowledge file, a skill section, or a worked example. Do not rewrite the procedure.

  • Experts would disagree → genuine ambiguity. Don't guess. Escalate to

the owner with the two defensible readings and let him pick. Record his choice as a position so it compounds.

Conversational form is a poor proxy for root cause: an expert correcting a conclusion can be exposing any of the three. Run the test on the materials, not on how the feedback was phrased.

Routing the Fix

  1. Recipe problem → edit the smallest procedure that owns the step

(skill SKILL.md, cron body, worker brief). Keep the edit minimal and re-run the failing scenario.

  1. Knowledge gap → write the missing fact where the agent will actually

load it next time (MEMORY.md, a skill's references/, a glossary). One durable location, not three.

  1. Ambiguity → ask the owner, one question, both readings stated plainly.

His answer becomes a position file / memory entry.

Fresh-Eyes Review (before landing)

Re-read the proposed fix as if you didn't write it — new pass, no memory of your rationale. Hunt for: contradictions with existing positions, edge cases the fix breaks, duplicated knowledge in two places, and token cost the fix adds to every future load. If it fails any of these, shrink it.

Output Contract

Every attributed mistake produces a lesson pair, stored where the fix landed:

  • what happened (one line, with evidence path)
  • attribution: recipe / knowledge / ambiguity (and why)
  • fix: the exact edit made
  • prevents: what this stops next time
  • confidence: high / medium / low

Operating Rules

  1. Diagnose before fixing. A fix without an attribution is a guess.
  2. One layer per fix. Never edit a recipe and add knowledge for the same

failure — pick the layer the test points to.

  1. Smallest edit that holds. If the fix needs more than a paragraph, the

attribution is probably wrong.

  1. Ambiguity always escalates. Never let the agent pick between defensible

readings silently.

  1. English or code only. No internal-machinery jargon in the lesson.
